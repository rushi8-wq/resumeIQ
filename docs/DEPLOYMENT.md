# Deployment

Scaffolding is included; cloud deployment has not been performed. This foundation is not yet the full production platform.

## MongoDB Atlas

Create a project and cluster, database user with only needed application permissions, and appropriate network restrictions. Set the SRV connection string in backend MONGODB_URI, including a database name. Use TLS, rotate credentials, and keep them out of git. Startup fails if database connection or index initialization fails.

## Render API

Connect the repository, select the included render.yaml blueprint, and set MONGODB_URI, CLIENT_URL (exact frontend origin) and JWT_SECRET (generated by blueprint). Backend installs workspace dependencies and starts Node. Set NODE_ENV=production. `/api/health` is the readiness endpoint. Render supplies PORT. The API trusts one reverse proxy; change that only to match verified infrastructure.

## Vercel frontend

Import the repository with root directory `client`, framework Vite, build `npm run build`, output `dist`. Enable access to files outside the root directory for the npm workspace lockfile. Set VITE_API_URL to `https://YOUR-API-HOST/api`, then build/deploy. client/vercel.json provides SPA fallback. Never put JWT_SECRET or API keys into VITE variables.

Prefer `app.example.com` and `api.example.com` on HTTPS with COOKIE_SAME_SITE=lax. With unrelated Vercel and Render domains use COOKIE_SAME_SITE=none and secure cookies (automatic in production), but browser third-party-cookie restrictions can still block sessions. Test in target browsers; use same-site custom domains or a same-origin API reverse proxy for reliable deployment. CORS must allow the exact frontend origin and credentials. No wildcard origin.

## Docker local development

```sh
cp server/.env.example server/.env
# Set a random JWT_SECRET first.
docker compose up --build -d
npm run dev -w client
```

Mongo volume persists across restarts. Do not run `docker compose down -v` unless deleting local data is intended. Dockerfile build context is repository root. Mongo binds loopback on the host; these local settings are not production database authentication settings.

## CI and release

GitHub Actions installs from lockfile, starts disposable MongoDB, runs auth/config tests, builds client and runs browser tests. It does not automatically provision or deploy cloud resources. Configure Vercel/Render git deployments only after checks pass. Add monitoring (Sentry or equivalent with PII filtering), shared rate limiter, dependency audit, backups, deletion/retention controls, password recovery and email verification before public production use. Add upload, AI and worker environment values only when corresponding milestones are implemented.

## Live verification checklist

Check HTTPS and readiness; register a test account; reload session; sign out; confirm replay rejection and private route protection; verify cookie flags, CSRF rejection and exact CORS. Confirm password hash in MongoDB and absence from responses/logs. Verify failed database connectivity returns no false healthy status. Later milestones add upload/analysis/provider and deletion smoke tests. Record real deployment URLs in README only after this succeeds.

## Milestone 4 Groq environment

Set AI_PROVIDER=groq, GROQ_API_KEY as a secret, GROQ_MODEL=auto (or a verified accessible model ID), and optional AI_DAILY_REQUEST_LIMIT in Render's backend environment. Restart/redeploy the API after changes. Never set these secrets in Vercel VITE variables or source. The existing Docker image installs groq-sdk through server dependencies and does not copy server/.env. Use Groq Cloud spend limits alongside application quotas. No provider credentials are required for automated tests, which use the isolated fixture API; this does not verify cloud deployment.
