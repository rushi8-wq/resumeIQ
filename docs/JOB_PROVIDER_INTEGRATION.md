## Adapter and synchronization

`server/src/services/jobs/provider.js` implements `searchJobs(filters)`, `normalizeJob(rawJob)`, `getJobDetails(jobId)` and `getSourceStatus()`. The Jobicy adapter deliberately retrieves a shared unfiltered corpus; application filters run locally. `getJobDetails` reads the adapter's last successful traversal; HTTP detail routes read persisted MongoDB records. No resume, search query, identity or location preference is sent upstream.

The adapter uses the documented HTTPS jobs endpoint, three sequential pages of 100 records, opaque cursors, 12-second request timeouts, an 8 MiB response limit per page, strict envelope validation and per-record validation. It refuses redirects. Invalid individual records are skipped; an all-invalid initial page, malformed JSON or upstream failure fails the pass. No automatic retry starts a second traversal. `partialCoverage` and skipped counts are returned. This is a bounded recent sample, not an exhaustive search of every provider vacancy.

A search triggers refresh when due. `JobProviderState` persists an atomic one-hour reservation across processes/restarts; in-process concurrent requests share one promise. Failed passes retain the reservation and prior cache. No background scheduler is installed. Status/detail/bookmark requests do not trigger upstream fetches. Unique source+ID and canonical URL indexes prevent duplicate records. Updated descriptions change their content hash.

Descriptions become plain text with `html-to-text`; React renders text, never source HTML. Scoring/display is limited to 15,000 characters, with an explicit truncation warning and source link. Missing metadata stays null/empty. All feed entries are remote; employment and level values come from the source. Location is an eligibility label, not proof that an applicant qualifies.

## Freshness and availability

The public source exposes a seven-day publication window. Each stored record has `fetchedAt`; discovery excludes records seven days after their last observation. Saved records remain readable with an expired warning, preserving bookmark references. Expiration does not assert that a position closed.

Response state is `live` only for a successful sync in that request, `cached` for a recent successful corpus, `stale` for usable older data/outage fallback, or `unavailable` when no usable corpus exists. A successful empty feed remains live/cached with zero matches. `lastVerifiedAt` is null: this version does not independently check each vacancy's availability. Fetch time is never labeled verification time. The source offers a separate status endpoint; it is not enabled here.

## Ranking and privacy

Saved structured resume data is scored with the unchanged Milestone 3 `scoreMatch` and configured weights. Local TF-IDF is used, with no external embeddings or Groq call. Job descriptions use the existing `parseJob`. Preferences explicitly filter candidates; they do not secretly boost scores. Sort is descending alignment or posted date, with stable ID tie breaks and pagination after filtering/ranking. Null scores sort last. Sparse descriptions and finite skill/qualification vocabulary can reduce confidence, particularly outside technology; general text matching still supports other industries.

Private `JobRecommendation` records cache results by owner, resume, job, resume revision, job content hash and scoring configuration version. Corrections or job/config changes cause recalculation. Seven-day TTL clears derived recommendation caches. Bookmarks and recommendation evidence are owner-scoped; deleting a resume cascades both. Shared public jobs remain. Credentials and resume bodies are not logged. Existing JWT/CSRF rules remain, with a jobs-specific 60 requests/minute/IP limit in addition to the global API limit. Shared rate-limit storage and crash-atomic multi-collection cleanup remain operational work.
